# 分析维度
请从以下维度逐一分析：

## 1. 安全风险
检查以下模式并提供具体文件位置：
- 硬编码的密钥、密码、Token（字符串中出现的 key/secret/password/token 赋值）
- SQL/命令注入风险（拼接 SQL 字符串、使用 subprocess/shell=True）
- 权限缺失（未检查用户身份的接口/函数）
- 敏感信息泄露（日志中输出敏感数据、错误信息暴露内部细节）

## 2. 稳定性风险
检查以下模式：
- 错误处理缺失（try/except 为空、未处理 None 返回、未检查文件存在性）
- 资源泄漏（未关闭的文件句柄、数据库连接、网络连接）
- 并发安全问题（全局状态修改、缺少线程安全措施）
- 异常传播路径（异常可能未被正确捕获）

## 3. 可维护性风险
检查以下模式：
- 代码重复（相同逻辑在多处重复出现）
- 高耦合模块（单一模块依赖过多其他模块）
- 过大文件/函数（超过合理长度的文件或函数）
- 缺少必要的文档注释

## 4. 技术债务
检查以下模式：
- 过时的依赖版本（requirements.txt/package.json 中的旧版本号）
- 不推荐使用的模式（deprecated API 调用、废弃的框架用法）
- 待办标记（代码中的 TODO/FIXME/HACK 注释）
- 硬编码的配置值（应使用环境变量或配置文件的常量）

## 5. 风险评估矩阵
将所有发现的风险汇总为表格，包含以下列：风险编号 / 风险描述 / 严重程度（高/中/低）/ 影响范围 / 代码位置 / 缓解建议。

## 6. 优先缓解计划
列出 Top 5 最紧急需要处理的风险，每项包含具体的修复建议和代码修改示例。

# 输出约束
- 输出完整的 Markdown 文档，以 # 标题开始
- 所有风险发现必须引用具体的文件路径和行号（或尽可能精确的位置）
- 风险按严重程度排序（高 > 中 > 低）
- 已有的架构分析和用户故事分析可作为上下文参考
- 使用中文编写
- 不确定的风险在句末标注 [推测]
