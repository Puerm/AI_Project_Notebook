# 分析维度

## 1. 一句话总结
用一句话说清楚这个项目是干什么的。如果一句话不够，可以加一句补充说明技术栈。

## 2. 模块地图
这是最重要的部分。列出项目的所有主要模块（目录/子项目），每个模块说明：
- **路径**: 模块所在的目录
- **它做什么**: 一句话说清楚职责
- **关键文件**: 2-3 个能代表该模块的文件

用表格呈现，让读者一眼看清项目全貌。像这样：
| 模块 | 路径 | 职责 | 关键文件 |
| ---- | ---- | ---- | -------- |

## 3. 模块之间的关系
描述模块之间怎么协作的：
- 谁调谁？（比如前端调后端 API，后端调 Worker 队列）
- 数据怎么流动？（比如用户请求 → Controller → Service → Database）
- 如果有独立的子系统（如 Python Worker、前端 SPA），单独说明它们的定位

用简单的箭头图或文字描述，不要画复杂的架构图。

## 4. 技术选型
列出关键技术组件和用途，引用依赖文件中的具体条目。用表格呈现。

## 5. 值得注意的设计
挑选 2-3 个项目中做得好的设计或值得注意的架构选择，用通俗语言解释为什么这样做是合理的。如果没发现特别的，就跳过这一节。

## 6. 可改进的地方
2-3 条具体的改进建议，按优先级排列。每条解释当前问题 + 改进方向。

# 输出约束
- 输出完整的 Markdown 文档，以 # 标题开始
- **面向新同事，用通俗语言。禁止使用以下术语：微内核、管道-过滤器、适配器模式、控制反转、依赖注入、关注点分离。用"怎么做的"替代"用了什么模式"。**
- 所有结论必须引用具体文件路径作为证据
- 不确定的信息在句末标注 [推测]
- 使用中文编写
