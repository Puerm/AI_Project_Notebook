# Spec: Harness 框架个性化部署

## 1. 要解决什么问题

Harness 框架从 AI Project Notebook 移植到新项目时，agent 定义、工作流、规则文件、项目背景等残留了上一个项目的"惯性"——语言栈假设、工具引用、领域约束没有根据新项目做适配，导致框架在新项目中"水土不服"，使用不顺畅。

**用户场景**：开发者将 harness 框架目录复制到新项目后，运行一个初始化命令，LLM 自动扫描新项目并生成个性化适配建议，开发者逐项确认/修正后完成部署，框架在新项目中运转顺畅。

## 2. 版本目标

提供 `harness-deploy` 命令：LLM 自动检测新项目 → 生成适配建议 → 人工逐项确认/修正 → 完成个性化部署。

## 3. 功能清单

### 本版本实现

| 功能 | MVP 描述 | 验收标准 |
| ---- | -------- | -------- |
| A. 项目背景自动填充 | 扫描目录结构、包管理文件、现有代码，推断语言/框架/领域 + 一句话描述 + 入口文件识别，写入 `project.yaml` 和 `CLAUDE.md` | 对新项目运行检测后，`project.yaml` 中的 language、framework、domain、description、entry_point 字段被正确填充 |
| B. Agent 定义适配 | 替换 agent md 文件中的工具/命令引用 + 示例代码片段适配 + 约束条件调整，7 个 agent 定义根据新项目技术栈更新 | 所有 agent md 中不再出现旧项目的技术栈特定引用，示例代码匹配新项目语言 |
| C. 工作流适配 | 根据项目类型调整工作流的阶段配置，跳过不适用的阶段 | 工作流文件中的 stages 配置与新项目类型匹配，不适用阶段被移除或标记为 skip |
| D. 规则文件适配 | 根据项目类型重写编码规则、安全规则、工作流规则内容，与新项目的语言栈和领域对齐 | 规则文件中的具体规范与新项目技术栈一致（如 TypeScript 项目生成 ESLint 相关规则） |
| E. 交互式确认流程 | 逐项展示适配内容，支持用户确认/跳过/手动编辑修改 | 每项适配展示后用户可选择确认(y)、跳过(n)、或打开编辑器修改(e)，修改后重新展示确认 |

### 暂不实现

- F. 一键执行模式（跳过确认全自动部署）

## 4. 风险与未决问题

### 风险

1. **项目解析不准确导致链式失败（首要风险）**
   - 描述：LLM 对新项目的语言/框架/领域判断错误，导致后续 agent、工作流、规则的适配全链偏离
   - 缓解思路：在检测阶段输出"检测摘要"作为确认流程的第一个环节，用户先确认项目画像是否正确再继续；同时建议检测逻辑使用多信号交叉验证（包管理文件 + 目录结构 + 代码特征），单一信号不匹配时标记为不确定并主动向用户澄清

2. **Agent 文件适配后丢失通用约束**
   - 描述：替换示例代码和工具引用时可能误删跨项目通用的编排逻辑或行为约束
   - 缓解思路：agent 文件中标记"通用区"和"可适配区"，只修改可适配区

3. **模板变量替换不完整**
   - 描述：`project.yaml` 中新增字段可能未被现有规则和工作流充分引用，导致部分适配流于表面
   - 缓解思路：适配完成后运行一致性检查，确保所有引用 `project.yaml` 变量的地方都有对应的值

### 未决问题

- 交互式确认流程中"打开编辑器修改"的具体交互方式（CLI 层面如何触发编辑器）
- 是否需要在确认阶段提供 diff 视图（修改前后对比），如果做归属哪个功能
