# Spec: v0.3.1 输出质量修复

## 1. 要解决什么问题

v0.3 在 BioTec 真机测试中暴露了四个问题：三个输出质量问题 + .env / API Key 引导缺失：module-map 文件级平铺 682 行无意义、data-flow 逐条 import 未聚合、directory-map 全展开 298KB 不可读。根因是 v0.3 spec 将"文件"等同于"模块"、未定义输出质量约束。v0.3.1 修复这三个问题，不新增功能。

## 2. 版本目标

修复 `analyze_project.py` 的输出质量和用户引导，使其对真实项目（200+ 文件）产生有意义、可配置的输出。

## 3. 关键概念定义

本次修复的核心概念：

| 概念 | 定义 |
| ---- | ---- |
| **模块** | 源码根目录下的一级子目录。一个模块 = 一个逻辑功能分组，包含若干相关文件 |
| **源码根** | 项目中包含实际业务代码的目录，通过 `__init__.py` 存在性 + import 关系自动识别（如 `back/python/paper_agent/`） |
| **模块依赖** | 模块 A 中任意文件 import 了模块 B 中任意文件 → "模块 A 依赖模块 B"。仅统计项目内部模块间依赖，stdlib 和第三方包不出现 |
| **数据流** | 从入口函数出发，经过哪些处理节点（函数调用）的路径。需要 LLM 语义理解，无 LLM 时不硬凑 |

## 4. 功能清单

### 本版本修复

| 功能 | 修复内容 | 验收标准 |
| ---- | -------- | -------- |
| **module-map.md 重构** | 从"每文件一行"改为"每模块一行"。模块 = 源码根下的直接子目录。每行包含：模块名（目录路径）、模块描述（概括该目录下所有文件）、主要函数/类摘要、**模块间依赖**（原来 data-flow 的依赖关系移入） | BioTec 项目 module-map 行数从 682 降到 20-40 行（目录级模块） |
| **源码根自动识别** | 扫描项目目录时自动识别源码根目录。算法：找包含 `__init__.py` 的目录树 + import 关系的深度最低的公共祖先。不依赖用户手动指定 | 对 BioTec 能正确识别 `back/python/paper_agent/` 为源码根 |
| **data-flow.md 重定义** | 内容改为真正的数据流分析（入口函数 → 调用链 → 数据变换节点）。LLM 启用时由 LLM 推断关键数据流路径。LLM 未启用时生成空模板，提示用户启用 `--llm` | 无 LLM 时不可强行生成虚假/低质量的数据流 |
| **directory-map.md 深度控制** | 新增 `--depth N` 参数（默认 3 层）。超出深度的目录折叠显示为 `├── storage/ (25 个子目录)` | 默认深度下 BioTec 的 directory-map 控制在合理篇幅（非 298KB） |
| **折叠显示** | 深层目录按类型折叠：全部同类型文件 → "Python 源码目录，X 个文件"；混合类型 → "N 个子目录，M 个文件" | 折叠后的目录树一眼能看出项目整体结构 |
| **.env 文件支持 + API Key 引导** | llm_assistant.py 新增 `.env` 文件读取（项目根目录 `.env`），`--help` 输出列出所需环境变量（`ANTHROPIC_API_KEY` / `LLM_API_KEY`），LLM 功能启用但缺 Key 时打印明确引导信息而非静默降级 | 用户能在 30 秒内完成"创建 .env → 填入 Key → 重跑 --llm" |

### 暂不修复

| 问题 | 说明 |
| ---- | ---- |
| overview.md 无 LLM 时质量差 | 核心原因是缺少 LLM 增强，属已知限制。暂无 LLM 时仍是模板描述 |

## 5. 风险与未决问题

| 风险/问题 | 处理策略 |
| --------- | -------- |
| 源码根自动识别在非标准项目结构下可能不准 | 留 `--source-root` 参数作为手动覆盖，自动识别失败时降级到项目根目录的直属子目录 |
| 模块描述在无 LLM 时仍需改进（v0.3 模板太通用） | 基于函数/类名做规则推断：如 `adapters/` + 包含 `*_adapter.py` → "适配器模块，集成外部数据源" |
