# Spec: v0.3.2 LLM 集成修复

## 1. 要解决什么问题

v0.3.1 `--llm` 实测暴露了 LLM 集成严重不完整：LLM 只增强了 overview 的一句话描述，模块描述仍走模板、data-flow 直接输出"LLM 未启用"、技术栈检测搜不到深层目录。v0.3.1 的 `--llm` 对 BioTec 产出的 module-map 只有 2 个模块（back/front），模块描述为"包含 576 个文件的 back 模块"，完全不可用。

## 2. 版本目标

让 `--llm` 真正生效——LLM 增强覆盖模块描述、数据流、技术栈推断全部三个维度。同时修复源码根检测和技术栈检测，使无 LLM 时输出也比 v0.3.1 有显著改善。

## 3. 关键概念定义

| 概念 | 定义 |
| ---- | ---- |
| **源码根** | 项目中包含实际业务代码的目录。一个项目可以有**多个源码根**（如前端的 `front/src/` 和后端的 `back/python/paper_agent/`） |
| **模块** | 每个源码根下的一级子目录 |
| **数据流路径** | 从一个入口函数出发，经过哪些关键函数调用到达数据存储或输出的路径 |

## 4. 功能清单

### 本版本修复

| 功能 | 修复内容 | 验收标准 |
| ---- | -------- | -------- |
| **LLM 模块描述增强** | `--llm` 时对每个模块调用 LLM 生成描述（自适应批量：≤10 个逐模块调，>10 个打包一批）。无 LLM 时保持模板描述 | BioTec 的模块描述从"包含 576 个文件的 back 模块"变为有意义的自然语言描述 |
| **LLM 数据流生成** | `--llm` 时对每个入口点调用 LLM 推断数据流路径（入口 → 关键函数调用链 → 输出）。无 LLM 时列出发现的入口函数列表，供用户手工追踪 | data-flow.md 不再出现"LLM 未启用"（--llm 模式），或至少列出入口函数（无 --llm 模式） |
| **LLM 技术栈/项目类型推断** | `--llm` 时由 LLM 综合目录结构 + package.json/pyproject.toml 等特征推断技术栈和项目类型 | BioTec 技术栈从"通用"变为"Python/TypeScript/Prisma"，项目类型从"通用项目"正确识别 |
| **多源码根支持** | 自动检测项目中多个源码区域（如 Python `__init__.py` 包树 + JS/TS 应用目录），分别做模块划分 | BioTec 能识别 `back/python/paper_agent/` 和 `front/` 为两个源码根 |
| **技术栈深目录检测** | 技术栈检测不再只搜根目录，改为递归搜索 3 层或到源码根深度 | BioTec 的 pyproject.toml（在 `back/python/`）和 tsconfig.json 能被搜到 |
| **无 LLM 数据流降级** | 无 `--llm` 时 data-flow.md 列出所有检测到的入口函数（CLI 命令、API 路由 handler、导出的主函数），不做虚假数据流推断 | BioTec 无 LLM 时 data-flow 至少列出 `back/python/paper_agent/main.py` 的 `build_parser` 等入口 |

### 暂不修复

| 问题 | 说明 |
| ---- | ---- |
| BioTec directory-map 包含 Notebook 自身部署的 `app/analyzer/` | EXCLUDE_DIRS 需新增 `app/`，但这是 init_project 部署策略问题，超出本次范围 |

## 5. LLM Prompt 设计要求

每个 LLM 调用必须附带足够的上下文。禁止只传模块名 + 函数列表。

### 上下文要求

| 增强点 | 必须附带的上下文 | 示例（BioTec adapters 模块） |
| ---- | ---- | ---- |
| **模块描述** | 项目名 + 源码根路径 + 同级其他模块名 + 该模块的依赖关系 + 关键文件名（前 5 个） | `项目: BioTec / 源码根: back/python/paper_agent / 同级模块: orchestrator, models, pipeline, storage / 关键文件: arxiv_adapter.py, pubmed_adapter.py, zhihuiya_adapter.py / 依赖: core/interfaces, models/record` |
| **数据流** | 入口函数名 + 所在模块 + 模块依赖图（简化版） | `入口: build_parser (cli/default_literature.py) / 模块依赖: cli→orchestrator→adapters→models` |
| **技术栈推断** | 特征文件路径 + 依赖列表（package.json deps + pyproject.toml deps 摘要）+ 目录结构概览 | `检测到: pyproject.toml, package.json, tsconfig.json, prisma/schema.prisma / Python deps: pymysql, ... / Node deps: @prisma/client, next, ...` |

### 输出要求

| 增强点 | 任务 | 输出格式 |
| ---- | ---- | ---- |
| **模块描述** | 根据模块名 + 关键文件 + 函数/类名 + 同级模块关系 + 依赖关系，判断该模块的职责 | **每个模块**输出一句中文描述，≤30 字。禁止出现"包含 X 个文件"等模板废话 |
| **数据流** | 根据入口函数 + 模块依赖图，推断数据从入口到存储/输出的关键调用链 | 每步格式：`入口 → 模块A.函数1 → 模块B.函数2 → ... → 输出/存储`，每步标注所属模块 |
| **技术栈推断** | 根据特征文件 + 依赖列表 + 目录结构，判断技术栈和项目类型 | 技术栈：列出具体框架/库名（如 Flask + Prisma + React）。项目类型：Web/CLI/库 + 简短说明 |

## 6. 风险与未决问题

| 风险/问题 | 处理策略 |
| --------- | -------- |
| 多源码根项目 LLM token 消耗大（模块数翻倍） | 自适应批量策略 + `--quiet` 模式下减少 API 调用 |
| 入口函数识别精度（LLM 未启用时） | 硬编码规则：Python 的 `argparse`/`click`/`typer` 调用点、JS/TS 的 `app.listen`/`express()` 调用点 |
| 数据流 LLM 质量依赖 LLM 自身的代码理解能力 | 提供模块关系图上下文，入口函数名前 5 条关键 import 作为补充线索 |
