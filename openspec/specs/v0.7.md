# Spec: Harness 反馈调节系统

## 1. 要解决什么问题

当前 harness 框架有反馈收集机制（error-log.md、improvement-log.md、workflow 回环），但缺少反馈调节闭环：
- 反馈日志积累了 19 条问题记录，但从未驱动过任何行为——变成"问题坟场"
- workflow 回环（explorer→planner-replan、tester→generator-fix）硬编码最多 2 次，不判断偏差是否在缩小，可能原地打转
- 规则文件（coding-rules、workflow-rules、data-safety-rules）完全静态，不随实战积累演化
- 编排器判断回环的方式是手工读文件第一段，脆弱且不通用

核心缺失：**检测到了偏差，但没有系统化的机制将偏差信号路由回系统进行调节**。

## 2. 版本目标

构建 harness 反馈调节系统 v0.1，实现三个核心能力：
1. 反馈信号标准化收集、跨 workflow 累积、重复模式检测
2. 基于重复模式的规则演化建议，以"不自动修改、但持续施加影响"的方式介入后续 workflow
3. 现有回环机制升级——共享状态快照 + 偏差趋势自适应

## 3. 功能清单

### 本版本实现

| 功能 | MVP 描述 | 验收标准 |
| ---- | -------- | -------- |
| 1. 反馈信号引擎 | 统一 FeedbackSignal 数据结构（类型、严重程度、关联规则、出现次数、时间戳）；`harness/state/` 目录存放状态快照和信号累积文件；每次 workflow 启动时自动加载历史信号，workflow 结束时追加新信号；重复模式检测——同一规则被命中 ≥3 次自动标记为"重复模式" | FeedbackSignal JSON schema 定义清晰；engine.py 能正确读取/写入/去重/检测重复模式；`harness/state/` 目录在 check_structure 中登记 |
| 2. 规则演化引擎 | 扫描 feedback 目录和 state 文件，当同一规则被命中 ≥3 次时生成 `harness/feedback/rule-evolution-proposal.md`（含变更理由、支持证据、建议修改的具体规则）；Planner 启动时若存在未处理建议，强制注入到 Planner 上下文 | 演化建议格式标准化；Planner 能感知并读取未处理建议；手动运行触发脚本可生成建议 |
| 3. 回环质量升级 | 共享状态文件 `harness/state/current-workflow.json` 记录阶段进展、偏差量、路由历史；编排器基于偏差趋势决策回环（偏差缩小→继续，偏差不变/放大→暂停）；回环数据写入 FeedbackSignal 反哺功能 1 | 编排器能读写状态快照；偏差趋势判断逻辑正确；回环记录被正确写入信号文件 |

### 暂不实现

- 框架自我修复（不修改 harness 自身代码）
- 自动化执行规则变更（只产出建议，不自动改规则文件）
- Web UI / 可视化仪表盘
- 修复 error-log 和 improvement-log 中已记录的框架级缺陷（留作未来测试用例）

## 4. 关键概念定义

- **反馈调节闭环**：检测偏差 → 反馈信号 → 条件路由 → 调节行为 → 恢复目标状态。参照控制论和 LangGraph 的共享状态 + 条件边模式
- **FeedbackSignal**：统一的偏差信号数据结构，替代当前分散的 error-log 条目、improvement-log 条目、review 问题——让机器可读、可累积、可比对
- **重复模式**：同一关联规则在反馈信号中出现 ≥3 次的状态，触发规则演化建议
- **偏差趋势**：当前回环与上一次回环的偏差量比较。偏差缩小 = 修正有效，偏差不变/放大 = 修正方向错误
- **规则演化建议**：机器产出的规则修改提案，含理由和证据，但需人工确认后才生效。在确认前通过强制注入 Planner 上下文施加影响

## 5. 风险与未决问题

- 反馈信号 JSON schema 的设计粒度——太细则噪音多，太粗则漏掉有效信号。需要在实际运行中迭代
- 重复模式阈值（≥3 次）是否合理，可能需要根据实战调整
- 偏差趋势的量化标准——explorer 的"计划粒度太粗"如何量化为可比对的数值（可能用行数、缺失字段数作为代理指标）
- `harness/state/` 目录可能随 workflow 次数膨胀，需要考虑归档或自动清理策略
