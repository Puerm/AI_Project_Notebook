# Spec: v0.4 渐进式披露分析引擎

## 1. 要解决什么问题

v0.3.x 的一次性全量分析在大型项目上产出不可靠：模块交叉污染、data-flow 虚构、入口检测失败、directory-map 信息过载。根因是"机器猜全部"——试图一次性分析所有源文件并生成完整理解，但提示词缺乏关键上下文，LLM 只能瞎猜。

v0.4 改为"渐进式披露"策略：模拟人类接手陌生项目的认知路径——先读 README 和关键配置文件建立整体框架，识别业务板块，标注置信度。把"这个项目大概有什么"诚实地告诉用户，让用户选择深入方向。

## 2. 版本目标

用少量关键文件（5-15 个）替代全量源码扫描，生成一份**项目概览**：一句话定位 + 业务板块列表（标注置信度）+ 板块间关系 + 建议下一步探索方向。不做细粒度模块分析。

## 3. 关键概念定义

| 概念 | 定义 |
|------|------|
| **业务板块 (Business Domain)** | 项目中的一个功能领域，可能对应一个或多个目录，也可能跨目录。例如 BioTec 的"用户与权限"涵盖 `auth/` + `users/` 两个目录。这是用户视角的"这个项目有哪些功能模块"，而不是代码视角的目录分组 |
| **引导文件 (Guiding Files)** | README.md、package.json、pyproject.toml、docker-compose.yml、Makefile、.github/ 下 CI 配置、框架配置文件（nest-cli.json、next.config.js 等）。人类上手新项目前几分钟会读的文件 |
| **渐进式披露** | 第一层只展示项目整体框架和板块列表；用户选择感兴趣的板块后，下一层再展开该板块的细节。每层消耗的 token 和精度逐层递进 |
| **置信度** | LLM 对每个推断结果标注高/中/低，让用户一眼判断哪些需要修正 |

## 4. 功能清单

### 本版本实现

| 功能 | MVP 描述 | 验收标准 |
| ---- | -------- | -------- |
| **引导文件收集** | 扫描并读取目标项目中人类认知项目的关键文件（README、依赖清单、Docker/CI 配置、框架配置），不读取业务源码 | 能识别并读取 5-15 个关键文件；对于缺失的文件（无 README 等），在输出中标注"缺失"而非静默跳过 |
| **目录结构摘要** | 收集一级+二级目录名（不展开文件），作为 LLM 判断板块的辅助输入 | 输出 ≤30 行的目录概要，UUID 目录和编译产物被折叠 |
| **LLM 业务板块识别** | 将引导文件内容 + 目录结构输入 LLM，产出业务板块列表（名称、描述、对应路径、置信度） | 板块数量合理（5-20 个）；每个板块有置信度标注；板块描述基于 README/依赖名的实际内容，不是模板填充 |
| **板块间关系推断** | LLM 基于 README 描述 + 依赖清单推断板块间的依赖/数据流关系 | 关系有依据来源（README 中写明的架构、package.json 的依赖分组等），不虚构 |
| **项目概览输出** | 单一输出文件（替代 v0.3 的 4 文件），包含：一句话定位、技术栈、板块表格、板块关系图、下一步建议 | 输出简洁（≤2 页），用户 2 分钟内能读完并形成认知 |
| **交互建议** | 概览末尾给出 2-3 个建议深入方向（如"想了解核心业务，建议从 X 板块开始"） | 建议基于实际文件量/复杂度分析，不是泛化建议 |
| **CLI 命令** | `analyze_project.py` 的新模式：默认运行新分析流程；`--depth=full` 保留旧版全量分析 | 默认模式 ≤15 秒完成（不含 LLM 调用），token 消耗可控 |

### 暂不实现

| 功能 | 说明 |
| ---- | ---- |
| 板块内模块展开（第二层） | 留到 v0.5+ |
| 细粒度文件/函数级分析（第三层） | 留到 v0.5+ |
| 交互式逐层探索界面 | 本版本仅输出文本，交互留到后续 |
| command-map 自动生成 | 留到后续版本 |
| data-flow 详细调用链 | 本版本只做板块间关系，不做函数级调用链 |
| 增量分析 | 留到后续版本 |

## 5. 风险与未决问题

| 风险/问题 | 处理策略 |
| --------- | -------- |
| 目标项目没有 README 或 README 内容空洞 | LLM 降级到依赖清单+目录名推断，置信度整体标低 |
| LLM 对大型 README 的上下文窗口限制 | 引导文件内容超过阈值时分段输入或摘要 |
| 业务板块划分的主观性——不同 LLM 可能输出不同的板块边界 | 置信度标注 + 输出中说明"板块划分基于 LLM 推断，可手动调整" |
| 如何定义"板块数量合理"（5-20 个） | Planner 需评估：板块太少失去意义，太多回到 v0.3 的细粒度问题 |
| LLM 的板块描述可能"脑补" | 要求 LLM 引用信息来源（README 哪一段、哪个依赖名），Plan 阶段设计 prompt 约束 |
